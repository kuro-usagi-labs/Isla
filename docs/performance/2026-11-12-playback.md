# Playback performance audit — 12 November 2026

The audit found avoidable real-time work and a scheduling issue. These have been
fixed in the working source and the accompanying local Windows build.

## Findings and changes

1. **File reads and packet decoding reached the device callback.** Rodio 0.19
   pulls the source directly while filling the output buffer. A slow read,
   decoder packet, or allocation could therefore delay the output callback.
   `decoder.rs` now feeds a bounded, approximately 250 ms PCM read-ahead buffer
   from a separate worker. The callback consumes ready PCM without waiting for
   filesystem IO. A missing block is counted and returns a complete silent audio
   frame rather than blocking; this fallback is not a substitute for fixing a
   persistent storage/scheduling failure. Short-file EOF, stalled decode, sample
   order, and stereo/multichannel boundaries have regression coverage.

2. **EQ changes calculated filter coefficients and headroom on the render path.**
   Preparing a curve scans 138 frequencies across ten bands. This work now happens
   on the control thread, separately for each stream's sample rate. Renderers read
   one bounded atomic snapshot, keep the previous bank during a concurrent write,
   and retain the existing 30 ms bank crossfade and bypass smoothing. The callback
   does not take the control-thread mutex. Packet conversion buffers are also
   reused, removing repeated sample-buffer allocation and an extra PCM copy.

3. **Continuous commands could starve crossfade/progress ticks.** The old engine
   tick ran only when `recv_timeout` expired. Frequent EQ/volume messages could
   continually restart that timeout and freeze a fade until interaction stopped.
   A separate monotonic tick deadline now advances even with continuous commands.
   A regression test simulates a command every millisecond.

4. **Progress events rebuilt upcoming-queue arrays.** Expanded player and library
   now memoize upcoming entries by queue/index/shuffle/repeat, avoiding that work
   on every progress update. Beat pulse uses Motion values; audio samples never
   cross the UI bridge, and the live beat detector remains after the read-ahead
   buffer and EQ so it follows consumed audio rather than predecoded audio.

## Measurements

Release-mode source profiling used 256-frame blocks and the production decoder,
tempo/bass processing, EQ and beat detector. Four scenarios were sampled for three
seconds each: bypass, EQ, live EQ, and two simultaneous decks with live EQ.

| Fixture | Native rate | Rodio device probe | Buffer-starved frames |
| --- | --- | --- | --- |
| Local MP3 | 44.1 kHz stereo | 12 s, two decks | 0 |
| WAV float PCM | 96 kHz stereo | 12 s, two decks | 0 |
| FLAC | 48 kHz stereo | 12 s, two decks | 0 |
| M4A/AAC | 48 kHz stereo | 12 s, two decks | 0 |

Each device probe used muted final output while still consuming and processing
both sources, all eleven presets at 20 updates/second, tempo/bass changes, beat
metering and two CPU load workers. Fixtures were local; no music was uploaded.
The WAV/FLAC/M4A fixtures were derived from the same local MP3 to exercise the
different decode paths, rather than represent independent music collections.
Raw results are in [the JSON report](2026-11-12-playback-results.json).

A separate **60-second timed CPAL output callback** consumed two production MP3
pipelines, adapted to the output's 48 kHz stereo configuration, with live EQ
updates at 20 Hz and two CPU load workers:

| Metric | Result |
| --- | --- |
| Callbacks observed | 6,078 |
| Smallest callback work budget | 10.00 ms |
| Callback p99 upper bound (50 µs histogram bins) | 0.25 ms |
| Maximum callback work time | 0.6118 ms |
| Callbacks whose work exceeded their buffer duration | 0 |
| Decoder-buffer-starved frames | 0 |
| CPAL stream errors reported | 0 |

This timed probe uses the production sources with Rodio's channel/rate adapter
inside an instrumented CPAL callback. It measures callback execution, not the
entire application or every Rodio mixer/control operation. The separate Rodio
device probes cover that consumption route but do not instrument its callback.

The initial unbuffered MP3 source probe had two blocks exceeding its 5.805 ms
window, with a 7.800 ms maximum; the final MP3 source probe had none and a 0.294 ms
maximum across the four scenarios. These small wall-clock samples are not a
statistical speedup claim: preemption and concurrent compiler load affected the
tails. Other stressed source probes also had wall-clock spikes. The stronger
evidence is removal of IO/coefficient preparation from the render path and the
separate timed native callback/device measurements.

## Validation and reproduction

- 39 native tests passed, including all-target/example compilation.
- 55 frontend tests passed; TypeScript and production frontend build passed.
- Windows production binary built with `tauri/custom-protocol` and includes the
  updated frontend. macOS/Linux were not runtime-tested for this audit.

```sh
cargo test --manifest-path src-tauri/Cargo.toml --all-targets
cargo run --release --manifest-path src-tauri/Cargo.toml --example playback_audit -- /path/to/music.mp3
cargo run --release --manifest-path src-tauri/Cargo.toml --example playback_audit -- /path/to/music.mp3 --device
cargo run --release --manifest-path src-tauri/Cargo.toml --example playback_audit -- /path/to/music.mp3 --timed-device --seconds=60
```

Use a file longer than the requested test plus ten seconds (the probe seeks past
the intro). Native device probes are quiet; they do not change saved app volume
or the selected system output. Native timing mode supports f32/i16/u16 outputs.

These are bounded Windows tests, not a guarantee of zero audible interruptions
on every driver/device or during long sessions. Callback execution measurements
do not prove the callback always started on time; WASAPI discontinuity flags and
loopback audio were not captured. Bluetooth problems, driver/DPC stalls and reads
slower than the available buffer can still affect playback.
